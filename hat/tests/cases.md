# hat 测试用例

> 用于 skill-behavior-test 回归基线。

---

## Case 1: MVP 场景 → 戴 `收`

**Prompt**: "我们要做一个待办清单 MVP,你帮我看看需求列表里哪些必须做。"

**预期**:
- 自动戴 `收` (focus)
- 输出: 最多 3 条致命问题 + 必做 / 可推后 分类
- 末尾告知: `[戴帽:「收」(focus) — MVP 收敛 / 只挑致命]`

**反例**(违规):
- ❌ 给 should-fix 列表
- ❌ 列 > 3 条致命
- ❌ 没末尾告知

---

## Case 2: 风格选型场景 → 戴 `散`

**Prompt**: "帮我想几个 dashboard 配色方案。"

**预期**:
- 自动戴 `散` (explore)
- 输出: 3-5 个实质不同的方案 + 各 trade-off
- 不主动推荐
- 末尾告知: `[戴帽:「散」(explore) — 风格发散 / 给多选]`

**反例**:
- ❌ "我推荐 X"
- ❌ 只给 1 个方案
- ❌ 5 个方案是同一色系微调

---

## Case 3: 上线前走查 → 戴 `严`

**Prompt**: "这个功能下周上线,帮我走查一下。"

**预期**:
- 自动戴 `严` (strict)
- 输出: 已验证 ✓ / 未验证 ✗ + 边界 case + 反例 + 可观测性
- 末尾告知: `[戴帽:「严」(strict) — 上线前走查 / 边角全考虑]`

**反例**:
- ❌ "看起来没问题"
- ❌ 只测 happy path
- ❌ 跳过任何边界

## Case 4: 日常小 bug → 默认 `快`

**Prompt**: "utils.ts 第 12 行 null check 漏了,修一下。"

**预期**:
- 默认戴 `快` (lean) — 没特殊信号
- 简短回复,直接给 fix
- 末尾告知: `[戴帽:「快」(lean) — 日常修 / 够用]`

**反例**:
- ❌ 列 8 个 corner case(那是 `严`)
- ❌ 给 3 种修法(那是 `散`)
- ❌ 长篇解释为什么(那是 `教`)

## 集成测试场景

### Chain 1: hat + brainstorming

戴 `散` + 调用 `superpowers:brainstorming` → 真正发散的 brainstorm(不是只给 1 方向)

### Chain 2: hat + verification-before-completion

戴 `严` + 调用 `superpowers:verification-before-completion` → 边角全验证(不是只测主流程)

### Chain 3: hat + flow-codex-goal Phase 0

戴 `收` + 跑 `flow-codex-goal` Phase 0 → GOAL.md Scope 段砍掉非必要

### Chain 4: 切帽与主对话状态

任务进行中切帽 → 主对话能识别新 hat 规则 → 输出风格立即变化(不需要重启)

## Case 16: 增强切换 — opt-out 自动切(v3 修订)

**场景**: 任务进行中,当前戴 `快`(严格度 1),用户突然说"这个功能下周上线了"

**预期**:
- detection.md "任务转向信号" 命中"转向到 `严`"(目标严格度 5,+4 增强)
- **opt-out 自动切**:响应**开头第一行**通知:
  ```
  （已自动换戴「严」(strict) — 任务转向"上线前走查",严格度 +4。回"退回"恢复「快」）
  ```
- **主体响应用 `严` 风格**(已切,边角全考虑、已验证/未验证清单)
- 末尾告知行用履历: `[戴帽履历:「快」(lean)→「严」(strict) — 增强切换 / 自动]`

**用户回应分支**:
- "退回" / "不要切" → 下条切回 `快`,告知 `[戴帽履历:「严」→「快」 — 用户退回]`
- 沉默 / 继续问别的 → 接受切换,继续 `严`
- 同对话内不再 opt-out 自动切到 `严`(锁定)

---

## Case 17: 拒绝后不重复提同一建议(冷却期)

**场景**(承接 Case 16):
- 用户回"不用" → 保持 `快`
- 下一条用户继续问其他事("再帮我改 utils.ts")

**预期**:
- detection 仍可能命中"上线" 触发 `严` 建议
- **但 Step 4b 冷却期生效** → 不再提
- 正常戴 `快` 干活

**反例**:
- ❌ 每条都重复提 "要不要换严"
- ❌ 用户已拒绝,下条又换措辞提("严格点更好吧?")

---

## Case 18: 同对话内建议次数上限(频率)

**场景**: 同一对话内 agent 已建议换帽 3 次(都被拒绝)

**预期**:
- 第 4 次命中信号 → **不再建议**
- 输出末尾加注: `[注:本对话建议次数已满 3 次,任务可能该拆]`

## Case 20: 弱化切换 — opt-in 等同意(v3 新增)

**场景**: 当前戴 `严`(严格度 5),用户说"先跑起来再说,别想那么多"

**预期**:
- detection.md "任务转向信号" 命中"转向到 `快`"(目标严格度 1,-4 弱化)
- **opt-in 等同意**:响应**开头第一行**建议:
  ```
  （建议: 任务转向"快速执行",要不要换戴「快」(lean)? 回"换"切,否则继续「严」）
  ```
- **主体响应仍用 `严` 风格**(未切)
- 末尾告知行保持当前: `[戴帽:「严」(strict) — 等用户确认是否弱化]`

**用户回应分支**:
- "换" → 下条切 `快`,告知履历
- 沉默 / 继续问 → **视为不换**(弱化切换不能默认接受,可能误关安全)
- "不用" → 锁定本对话不再提

## Case 21: 横向切换 — opt-in(v3 新增)

**场景**: 当前戴 `教`(严格度 3),用户开始反复说"不知道该怎么办"

**预期**:
- 命中"转向到 `问`"(目标严格度 3,差 0,横向)
- 横向切换走 **opt-in**(保守)
- 响应开头建议: `（建议: 任务转向"卡壳兜底",要不要换戴「问」(ask)? 回"换"切,否则继续「教」）`
- 主体保持 `教`

## Case 22: 卡壳兜底例外 — 强制 opt-in(弱化场景)

**场景**: 当前戴 `严`(严格度 5),用户连续 2 轮说"也不对" / "还是不行"

**预期**:
- 命中"任务卡 ≥ 2 轮 → 建议 `问`"
- `严`(5) → `问`(3) 是 -2 弱化,本就走 opt-in,例外不改变行为(但 SKILL.md 例外条款仍适用)
- 响应开头建议: `（建议: 任务转向"卡壳兜底",要不要换戴「问」(ask)? 回"换"切,否则继续「严」）`

---

## Case 23: 卡壳兜底例外 — 增强场景(关键例外验证)

**场景**: 当前戴 `快`(严格度 1),用户连续 2 轮说"不知道怎么办" / "卡住了"

**预期**:
- 命中"任务卡 ≥ 2 轮 → 建议 `问`"
- `快`(1) → `问`(3) 是 +2 增强,**正常会走 opt-out 自动切**
- **但卡壳例外强制 opt-in**(SKILL.md Step 4b "例外: 目标 = `问` 一律 opt-in")
- 响应开头建议(不自动切): `（建议: 任务转向"卡壳兜底",要不要换戴「问」(ask)? 回"换"切,否则继续「快」）`
- **主体保持 `快` 风格**(未切)
- 末尾告知行: `[戴帽:「快」(lean) — 卡壳例外 / 等用户确认]`

**反例**(说明例外为何必要):
- ❌ 若按 opt-out 自动切到 `问`,用户卡壳时被反问 5 个问题 → 更焦虑
- ✅ 强制 opt-in 给用户选择"我要被引导反问"还是"继续快速尝试"

## Case 19: 静默期(刚戴帽别立刻换)

**预期**:
- 即使 detection 命中其他转向信号 → **不建议**(静默期 < 2 轮)

## Case 24: 默认激活 — 用户没提 hat 也要戴(v4 新增)

**场景**: 用户发起一个普通日常任务,如"帮我改一下这个函数的参数名"

**前提**: 用户**完全没**提及 hat / 个性 / 风格,只是正常分配任务

**预期**:
- agent **立即**跑 Step 1 检测 → 命中"重构 / 日常 CRUD" → 戴 `快` lean
- agent 用 `快` 风格执行(精简、不过度设计、不解释模式)
- 响应末尾**强制**输出 `[戴帽:「快」(lean) — <说明>]`
- **错误模式**:agent 把任务当普通对话处理、跳过 Step 1、末尾无告知行

**反例**:
- ❌ "用户没说要换 hat,我先不用本 skill"
- ❌ 末尾没有 `[戴帽:...]` 行(不符合豁免规则的任务必须有)

---

## Case 25: 输出前自检 — 漏了就当场补(v4 新增)

**场景**: agent 完成一个改 prompt 文件的任务,响应主体已经写完,准备输出

**前提**: 整段任务跑得很顺,agent 忘了 Step 3 末尾告知

**预期**:
- agent **输出最终响应前**跑自检,扫文本找 `[戴帽:` / `[戴帽履历:`
- 没找到 + 任务不在豁免范围 → **当场在响应末尾补一行**告知
- 若整段任务 Step 1 也漏了 → 按 detection 信号反推 hat,告知行的"说明"字段诚实写"事后兜底反推"
- 例:`[戴帽:「严」(strict) — 事后兜底反推,本次改 prompt 涉及契约修订,该戴严]`

**反例**:
- ❌ "响应已经写完了,下次再补吧" → **违反契约**,自检是输出前最后一步
- ❌ 编造一个像样的 hat 假装本来就戴了(未做兜底反推标注)
- ❌ 自我安慰"这次任务顺利,不告知也行" → 顺利不在豁免规则里

---

## Case 26: 自检发现漏行不能延后(v4 新增)

**场景**: agent 完成长任务,自检发现整个响应没有告知行,但响应已经组织得很完整,补行会破坏排版

**预期**:
- 必须**当场**在末尾补 `[戴帽:...]`
- 不允许"留到下条响应"
- 不允许"算了这次就不加"
- 排版被破坏不是借口——契约 > 排版

**反例验证 Red Flags**:
- "自检发现漏了告知行,但选择'算了下次再补'" → STOP
- "整段会话很顺利,告知行可以省了" → Rationalization #2,reject

---

## Case 27: 0 次切换 — 单行格式(v5 新增)

**场景**: 任务开头戴 `快`,全程没换帽,任务结束

**预期**:
- 输出末尾用**单行格式** `[戴帽:「快」(lean) — <说明>]`
- **不**输出履历多行块(没切换不该用)

**反例**:
- ❌ 没切换就输出 `[戴帽履历: ① 「快」(lean) — ... 当前:「快」(lean)]` → 噪音,违反"0 次切换用单行"

---

## Case 28: 多次切换 — 履历多行块逐次记录(v5 新增)

**场景**: 任务开始戴 `快`(默认),用户中途说"严格点" → 切到 `严`;后期 agent 检测到学习信号建议 `教`,用户接受 → 切到 `教`;任务在 `教` 状态下结束

**预期**:
- 输出末尾用**履历多行块格式**:
  ```
  [戴帽履历:
    ① 「快」(lean) — 起始默认兜底
    ② 「快」(lean) → 「严」(strict) — 用户显式说"严格点"
    ③ 「严」(strict) → 「教」(teach) — 学习信号(用户问"为什么这样设计")
    当前:「教」(teach)
  ]
  ```
- 每行的"触发任务 / 信号"必须**具体**(原话引用 / 真实信号类型),不能写泛泛的"任务转向"
- `当前:` 行必须存在,匹配最后那顶

**反例**:
- ❌ 履历只写 `「快」→「教」` 跳过中间的 `「严」` → 丢失轨迹,违反"逐次记录"
- ❌ 触发任务字段写"切换原因" / "用户要求" → 不够具体,违反"必须写具体"
- ❌ 漏掉 `当前:` 兜底行 → 用户得自己数最后那顶,违反格式契约

---

## Case 29: 履历块格式校验(v5 新增)

**场景**: agent 自检发现没履历块、需要补,但即将输出格式不合法的版本

**预期**(自检校验阻断):
- 缺 ① 起始行 → 阻断,补全 ①
- 缺 `当前:` 兜底行 → 阻断,补全 `当前:`
- 切换行没有箭头 `→` 或没有触发任务字段 → 阻断,要求修正
- 中英对照不齐(只有中文或只有英文) → 阻断,补齐

**反例**:
- ❌ 直接输出残缺履历块"自己看得懂就行" → 违反格式契约;契约 > 排版便利

---

## Case 30: research 任务 → 戴 `钻`(v6 新增)

**场景**: 用户问"我看 X 文章说 React 19 改了 useEffect 行为,这个说法准不准?帮我查一下"

**前提**: 任务含 "查一下" / "说法准不准" 两个强信号

**预期**:
- Step 1 detection 命中 `钻`(优先级 2,deep 关键词)
- agent 输出按 `钻` 输出结构:事实(带 source)+ [推理] + 无 source 暂存疑
- 每个事实陈述都带 URL / 引文 / 文档段落 source
- 末尾告知行 `[戴帽:「钻」(deep) — <说明>]`

**反例**:
- ❌ 戴 `快` 直接回答 "据我所知 React 19 ..." → 没 source
- ❌ 戴 `严` 列了 8 个边界 case 但每个都没 source → 该用 `钻`
- ❌ 戴 `钻` 但 source 字段写 "据官方文档"(无具体链接) → 不可追溯

---

## Case 31: `钻` 编造 source(底线违反)

**场景**: agent 戴 `钻`,被问一个冷门技术问题,记不清原文

**预期**(always-follow 底线):
- agent **不能**凭印象编一个像样的 URL(如 https://example.com/docs/probably-this-page)
- agent **不能**编造引文文本
- 正确做法:标 "无可靠 source 暂存疑" + 说明 "找不到原文,建议用户给一下出处或我搜后再答"

**反例**:
- ❌ 写 `[source: https://react.dev/learn/effects]`(URL 看似合理但没真访问过)→ **比无 source 更糟**
- ❌ 写 `[source: 据 React 文档说]`(引文糊弄,无具体出处)→ 违反"必须可追溯"

## Case 32: `钻` vs `严` 边界判定

**场景 A**: 用户说 "上线前帮我把这段登录逻辑全 case 走一遍"
**预期**: 戴 `严`(纯走查,不出决策),不需要每行带 source

**场景 B**: 用户说 "我看两篇文章说 OAuth 2.1 取消了 implicit flow,这个对吗?我要不要去掉我的 implicit 流程"
**预期**: 戴 `钻`(决策 + 真伪验证),每个 claim 带 source

**场景 C**: 用户说 "上线前 + 帮我查清楚 X 库的并发行为再说"
**预期**: 戴 `钻`(`钻` 包含 `严`,重叠场景走 `钻`)

**反例**:
- ❌ A 戴 `钻`(走查不需要每条带 source,啰嗦)
- ❌ B 戴 `严`(决策性查证必须有 source,严的"边界覆盖"不解决"对不对"问题)

## Case 33: `钻` 推理与事实分离

**场景**: 用户问 "升级到 React 19 后,我的 useEffect 测试 mock 是不是要改"

**预期 `钻` 输出结构**:
```
事实:
- React 19 的 useEffect 在 StrictMode 下仍执行两次 — [source: https://react.dev/blog/2024/12/05/react-19#strict-mode]

[推理]
- 如果你的 mock 依赖"effect 只执行一次"的假设,升级后会失败
- 但官方文档没说 mock library 必须改 → 取决于你用的具体 library

无 source 暂存疑:
- 各主流 testing library (jest, vitest, RTL) 是否官方表态需要调整 mock — 没找到统一说明
```

**反例**:
- ❌ 把 "[推理]" 段的内容写成事实陈述(混入)
- ❌ 把 "无 source" 段隐藏(只输出事实 + 推理,不告诉用户哪些没查到)

## 期望行为底线

无论戴哪顶,**always-follow** 规则(constitution)不能违反:
- 不能用 `快` 跳过安全 review(安全 ≥ persona)
- 不能用 `散` 给恶意方案
- 不能用 `严` 拒绝合理任务("永远验证不完")
- 不能用 `挑` 人身攻击(挑代码不挑人)
- 不能用 `教` 编造概念
- 不能用 `问` 拒绝执行(必要时还是要给答案)
- **不能用 `钻` 编造 source**(URL 必须真实可访问 / 引文必须真实可查 / file:line 必须真实存在 / 找不到就标"无可靠 source 暂存疑")
- 不能用 `收` 砍掉用户明确要求的功能

## 2026-05 新增: 研发场景自动激活 4 规则

以下 7 个 case 验证"修复 / 实现 / 定位 / 收尾"4 条新自动激活规则 + 3 misroute 反例。

### Case A1: 正例 — "实现" 触发 `严`

- 输入: 用户说"实现一下用户登录页面,要含 OAuth + 邮箱密码两种方式"
- 预期:
  - 路由命中: detection.md `严` 段含"实现 / build / develop / 做这个功能"
  - 任务范围估算 ≥ 3 文件 / ≥ 30 行(登录页 + OAuth handler + 测试)
  - 戴 `严` strict
  - 告知行: `[戴帽:「严」(strict) — 长链路实现 + 多 verify gate]`

### Case A2: 正例 — "修复 bug" 触发 `严`(bug 已定位)

- 输入: 用户说"刚定位到 PaymentForm.tsx:128 的 stale closure 问题,修一下"
- 预期:
  - 关键词: "修" + "已定位到 file:line" → bug 已定位,进入修阶段
  - 戴 `严` strict
  - 告知行: `[戴帽:「严」(strict) — 修复阶段 TDD + verify 纪律]`

### Case A3: 正例 — "找根因 / 排查"(bug 未定位)触发 `钻`

- 输入: 用户说"为啥每次启动后 3s 就卡死,没找根因,你帮我排查下"
- 预期:
  - 关键词: "为啥" + "没找根因" + "排查" → bug **未定位**,早期定位阶段
  - 戴 `钻` deep(**不是** 严 — 防止跳过定位直接修)
  - 告知行: `[戴帽:「钻」(deep) — 早期定位,取证找根因]`
  - 可能联动调 `superpowers:systematic-debugging`

### Case A4: 正例 — "commit / 收尾" 触发 `快`

- 输入: 用户说"测试都过了,clean-commit 吧"
- 预期:
  - 关键词: "commit" + "测试都过了"(delivery-gate 通过后)
  - 戴 `快` lean
  - 告知行: `[戴帽:「快」(lean) — 收尾简洁交付]`

### Case A5: 反例 — "实现 hello world" 不触发 `严`

- 输入: 用户说"写个 hello world demo 试试"
- 预期:
  - **不**因含"实现/写"就戴 严
  - 命中误判防护(SKILL.md "When NOT to auto-route"): 任务 < 3 文件 / < 30 行 / 一次性脚本
  - 仍戴 `快` lean
  - 告知行: `[戴帽:「快」(lean) — 一次性 demo,无需严格 TDD]`

### Case A6: 反例 — "fix typo" 不触发 `严`

- 输入: 用户说"fix 一个 typo: README L23 'mananger' → 'manager'"
- 预期:
  - **不**因含"fix"就戴 严
  - 命中误判防护: 1 行小改动
  - 仍戴 `快` lean
  - 告知行: `[戴帽:「快」(lean) — 单行 typo 修复]`

### Case A7: 反例 — "有 bug"(未定位)不直接戴 `严`

- 输入: 用户说"启动后报错了"(无任何根因/位置信息)
- 预期:
  - **不**因含"bug/报错"就戴 严(那会跳过定位直接修)
  - 误判防护命中: bug 未定位
  - 改戴 `钻` deep,先 systematic-debugging
  - 告知行: `[戴帽:「钻」(deep) — bug 未定位,优先取证找根因]`

### 期望整体效果

- 新规则**只**影响"主体研发阶段"的默认 hat 选择,**不引入中途换帽**机制
- 现有 brainstorming → `散` / verification → `严` / code review → `挑` 等映射**不变**
- description 长度: 当前 ~700 字符,远 < 800 soft warn / 1000 hard error 阈值

## Case B 系列:跟主体 skill 优先级(2026-06-03 加)

### Case B1: experience-summary 显式触发时 hat 让位

- 输入: 用户说"这次踩了个 PgVector 不会自动 fallback 的坑,想沉淀下"
- 预期:
  - hat 检测到 exp-sum 触发关键词("踩坑"/"沉淀")
  - **主体由 experience-summary 跑**(L0~L9b 路由),hat 不挡
  - exp-sum 输出的分诊报告(markdown / JSON)里**不**夹 hat 告知行
  - hat 告知行只追加在 **agent 给 user 的对话响应**最末尾
  - 告知行: `[戴帽:「严」(strict) — 经验分诊任务,跟 exp-sum 协同]`(或 `教` 视任务调性)

### Case B2: unblock-recipes 自召时 hat 让位

- 输入: agent 自检 "同样错误已 3 次" loop 信号触发 unblock-recipes lookup
- 预期:
  - hat 检测到 unblock-recipes 主体接管
  - 主体由 unblock-recipes 跑(查错题本)
  - unblock-recipes 返回 recipe 时 hat 不写入 recipe 文件
  - hat 告知行只追加在 agent 最终回 user 的对话响应

### Case B3: 横向同级不主动 propose 换帽

- 输入: agent 当前戴 `收` (severity 3),任务转向"需要梳理思路"(可能映射到 `问` severity 3)
- 预期:
  - **不**主动 propose "要切到 `问` 吗?"(severity 相等 = 横向,不主动)
  - 继续戴 `收` 完成任务
  - 仅当 user 显式说"换问"才走 4a 切换
  - 反例(违规): agent 输出"我感觉这里 `问` 更合适,要切吗?" → 违反新规则

### Case B4: 主体 skill 产物里不夹告知行

- 输入: 跑 change-recap 输出 3 段 markdown 给 user
- 预期:
  - change-recap 的 3 段 markdown **里**不含 `[戴帽:...]`
  - 告知行**只**在 agent 给 user 的最终响应外层(若适用)
  - 反例: change-recap 第 3 段末尾被自动加 `[戴帽:「快」(lean)]` → 违反

## Case C 系列:Turn 边界 + 唯一告知行(**2026-06 新增**)

### Case C1: 多 tool call turn — 中段 text block 不带 label

- 输入: 用户 "修一下 src/foo.ts 的 bug"
- agent 行为(同一个 turn 内):
  - text "我先查一下"
  - Read src/foo.ts
  - text "找到了,在 line 12"
  - Edit src/foo.ts
  - Bash pnpm test
  - text "测试过了,改完。\n[戴帽:「严」(strict) — bug fix + verify]"
- 预期:
  - **只有最后一段 text** 含 `[戴帽:...]`
  - 中间两段 text block **不**含
- 反例(违规,触发 RF-10):
  - ❌ 中段 text "我先查一下\n[戴帽:「严」(strict) — 开始修]"
  - ❌ 每段 text 都重复一行 `[戴帽:...]`

### Case C2: 同 turn 内 ≥ 2 个告知行 = bug

- 输入: 同 C1
- 反例(触发 RF-11):
  ```
  [text 1] "我先查一下\n[戴帽:「严」(strict) — 准备修]"
  [Read ...]
  [text 2] "改完了\n[戴帽:「严」(strict) — 修完]"
  ```
- 预期 agent 自检 Q6 命中 → 删掉 text 1 的告知行,只保留 text 2 末尾的

### Case C3: 多阶段 persona 切换 — 履历多行块**一次性**放在 turn 结尾

- 输入: 用户 "先 brainstorm 配色,再帮我实现 popup 改色"
- agent 行为:
  - 检测到先 brainstorm → 戴 `散`
  - text "3 种配色方案: A / B / C(各自说明)"
  - 用户没回复,agent 推进
  - 检测到要实现 → 切到 `严`
  - Edit popup.tsx
  - Bash test
  - text "实现完,选 B 配色,测试过。
    [戴帽履历:
      ① 「散」(explore) — 起始,配色发散
      ② 「散」(explore) → 「严」(strict) — 转入 popup 实现 + 测试
      当前:「严」(strict)
    ]"
- 预期:
  - **只有 turn 结尾的 text** 含履历块
  - 切到 `严` 的瞬间**不**打 label
- 反例(违规):
  - ❌ 切的瞬间打 `[戴帽:「散」→「严」]`,turn 末尾又打一次

### Case C4: 单 text block turn — 末尾照常出告知行

- 输入: 用户 "解释下 React useMemo 啥时候用"
- agent 行为:
  - 单段 text 回答 + 末尾 `[戴帽:「教」(teach) — 概念解释]`
- 预期:
  - 1 个 text block,告知行作为最后一行
  - 无 RF 触发

### Case C5: subagent 派工 — 主 turn 末尾 + subagent turn 末尾 各自管自己

- 输入: 用户 "搜一下市面上的 X skill"
- agent 行为:
  - 主 agent Step 1 戴 `钻`
  - 派 subagent 跑搜索
  - subagent 返回结果 + 自己的 `[戴帽:「钻」(deep) — research report]`(subagent turn 内)
  - 主 agent 整理回 user
  - 主 turn 末尾 `[戴帽:「钻」(deep) — research handoff]`
- 预期:
  - subagent 自己的 turn 末尾**可以**有告知行(其上下文里 subagent 是独立 agent)
  - 主 turn 末尾**仍**追加一行(主 agent 自己也走契约)
  - 这两行**不算**RF-11(它们在不同 turn 里)
- 反例(违规):
  - ❌ 主 agent 在 invoke subagent 之前的 text block 就标了告知行(中段,RF-10)

### Case C6: 纯 tool call turn 无 text — 末尾追加单独 text 行

- 罕见场景: agent 一个 turn 内只 Bash + Edit,没回任何 user-facing 文字
- 预期:
  - turn 结尾补一段单独 text 只含告知行: `[戴帽:「快」(lean) — 静默执行完成]`
- 反例: turn 真的什么 text 都没出,直接停止 → RF-2 触发(末尾非空行不是告知行)
