# Failure Modes — director-pm 红线 / 自我合理化 / 常见错误

> 本文件承载主体 SKILL.md `## Red Flags` 段的完整清单。主体只保留入口说明 + 高频速记，详细全在此。

## 1. Red Flags — STOP（任一命中必须停下）

- **没搞清"为谁解决什么问题、不做的代价"就写需求 / 排优先级 / 放行功能** —— 回 `clarify`，不准往下走
- **把"技术可行 / 实现简单"当作"该做"的理由** —— 该不该做看用户价值与机会成本，不看实现难度
- **scope 膨胀 / 需求镀金不砍** —— 默认砍，不默认加；保留必须说清解决的真问题
- **优先级全 P0、没有"先不做"列** —— 不做取舍 = 没做优先级判断
- **把"该不该做 / 先做哪个"的判断甩回用户** —— 产品经理必须给带依据的推荐 + 留痕，用户只在闸口确认
- **无证据却断言"有价值 / 该做"** —— 必须标 `evidence: assumption` + 待验证项
- **越界**：技术栈选型（→ director-architect）/ 视觉交互（→ director-design）/ 开工 intake（→ project-prep）

## 2. Rationalizations to Reject（自我合理化话术）

| 说辞 | 现实 |
|------|------|
| "老板想要，那就做" | 老板想要 ≠ 用户需要。把它转成"解决谁的什么问题"再判断 |
| "竞品都有这功能" | 竞品有不是价值证明；先问你的用户为此痛不痛 |
| "反正实现起来不难，顺手做了" | 技术成本低 ≠ 该做；它仍有维护成本和注意力成本 |
| "都挺重要的，都排 P0" | 全 P0 = 没优先级。强制排序 + 必须有"先不做" |
| "先把功能都列出来就是需求了" | 功能列表不是需求；没有问题/用户/AC 的列表会让下游全漂 |
| "你觉得这个该做吗" | 把判断推给用户 = 失职。给推荐 + 依据，用户确认 |
| "空态/异常/边界以后再说，先定 happy path" | AC 不覆盖边界 = "做完了"无法客观判定 |
| "MVP 先做全一点免得返工" | MVP 是最小**可验证**，不是最小**完整**。膨胀的 MVP 验证不了假设 |

## 3. Common Mistakes（常见执行错误）

- 跳过 `clarify` 直接 `prd` / `prioritize`，把模糊需求固化成文档
- PRD 的验收标准写成主观描述（"体验流畅"），无法客观判定
- 优先级排序不写依据（RICE 的各项打分 / MoSCoW 归类理由缺失）
- critique 给了 verdict 但不留痕"砍了什么、为什么砍"
- 把产品评审做成功能罗列，不评用户价值（维度 8 失分）
- 越界给出技术栈 / 视觉方案，而不是移交对应 director-*
