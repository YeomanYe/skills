# Mirroring Checklist

当用户说「按 X 项目做规范」「对齐 Y 的规则结构」时，`director-architect` 在 Research Phase
**Step 5** 用本清单检查参考项目的可借鉴性。

**核心原则**：**不机械搬运**。参考项目的结构必须先对齐当前项目的栈和场景，才能借鉴。

## 触发条件

以下任一信号触发 Step 5：

- 用户提到具体项目名、本地路径、git URL（如 "按 shadcn-admin 那套做"）
- 用户说 "对齐 X" / "参照 Y" / "镜像那个项目"
- Upstream 在 handoff payload 传了 `reference_project` 字段

## 获取参考项目内容

| 来源 | 命令 |
|---|---|
| 本地路径 | `ls <path>/docs/` + 读关键文件 |
| 远程 git URL | `git clone --depth 1 <url> $(mktemp -d)/ref-project` |
| GitHub 仓库（公开） | 同上 |

**超时**：`git clone` 30s 内未完成 → 降级为"只评估本项目"分支，在报告显式标注。

## 兼容性检查（**必须全部通过才能照搬**）

### 1. 栈兼容性

参考项目的栈 == 当前项目的栈？

- **完全一致**（如都是 `next + tailwind + shadcn`）→ 结构可大幅借鉴
- **部分重合**（参考是 `next`，当前是 `remix`）→ 只借鉴跨栈通用的部分（如 `architecture/`、
  `ai-guide/`），栈特定规则（如"Server Component 边界"）**不直接搬**
- **完全不同**（参考是 `next`，当前是 `go + rust`）→ 只借鉴**方法论**（分域思路、入口路由
  策略），**不借鉴**任何具体规则文件

### 2. 规模兼容性

| 参考项目规模 | 当前项目规模 | 建议 |
|---|---|---|
| 大项目（>50 规则文件） | 小项目（<10 文件） | **不要**全搬，只借鉴 `CONTRIBUTING + 1-2 domain` 的骨架 |
| 小项目 | 大项目 | 参考可能不够用，需自己补 |
| 规模相当 | — | 可大幅借鉴 |

### 3. 团队兼容性

参考项目是团队协作（多人 + PR review 流程）？当前项目是个人 / 1-2 人？

- 团队 → 个人：删掉协作流程类规则（如"PR 必须 2 approval"）
- 个人 → 团队：补齐协作流程

### 4. AI 协作兼容性

参考项目有 `AGENTS.md` / `ai-guide/` 这类 AI 规则？

- 都有 → 可借鉴 AI 规则路由
- 参考没有，当前需要 AI 协作 → 参考的方法用不上 AI 维度，需自己补
- 参考有，当前不用 AI → 删掉 AI 规则

## 借鉴清单（**逐项判断**）

对参考项目的每个组成部分：

| 组成 | 默认是否借鉴 | 判断要点 |
|---|---|---|
| 总入口文件（`CONTRIBUTING.md` 的存在 + 角色） | 几乎总是借鉴 | 唯一入口的原则跨栈通用 |
| 分域目录骨架（`architecture/coding/ui/ai-guide/`） | 通常借鉴 | 分类方法跨栈通用 |
| 每域 `index.md` + `rules.md` 双骨架 | **必须借鉴** | 是 director-architect 的硬要求 |
| 栈特定规则文件（如 `coding/server-components.md`） | 仅当栈一致 | 栈不同时不搬 |
| 工程命令清单（`completion.md` 里的具体命令） | 仅当工具链一致 | npm vs pnpm vs bun 不同时不搬 |
| 团队协作流程文件 | 仅当协作模式一致 | 个人项目不需要 |

## 不可借鉴清单（**永远不搬**）

- 参考项目的具体业务规则（如"用户表必须有 deleted_at"）—— 业务相关
- 参考项目的具体设计 token 值（颜色、字号）—— 视觉相关，归 `director-design`
- 参考项目的 README / CHANGELOG —— 项目对外说明，归 `flow-project-finish`
- 参考项目的法律 / 合规文档 —— 项目自身或法务流程
- 参考项目的 secret / 凭据 / 部署配置具体值 —— 安全相关

## 在 Output Contract 怎么写

研究报告的"参考项目对齐"段必须如实写：

```md
### 参考项目对齐
- 参考项目路径: <path 或 URL>
- 参考项目栈: <list>
- 当前项目栈: <list>
- 兼容性判定: 完全一致 | 部分重合 | 完全不同
- **借鉴的模式**:
  - <模式 1>: <为什么借鉴 + 怎么适配当前项目>
  - <模式 2>: ...
- **不适用的部分 + 理由**:
  - <部分 1>: <为什么不搬>
  - <部分 2>: ...
- **栈特定差异需要自己补的部分**:
  - <如 "当前项目用 svelte，参考项目用 next，svelte 的 runes / store 规则需自己写">
```

## 常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| `cp -r ref-project/docs/* ./docs/` 全搬 | 把不适用的规则塞进来，长期负担 | 按上述清单逐项判断 |
| 借鉴了文件名但内容空着 | 看起来对齐，实际未落地 | 文件名借鉴 + 内容自己写 |
| 把参考项目的具体业务规则搬过来 | 引入无关业务噪音 | 只借鉴**方法论 / 骨架** |
| 默认借鉴一切，再问用户"哪些不要" | 推断责任给用户 | 先自己判断，**只问真正模糊的点** |
