# Approval Gate Format

`director-architect` 在 Research Phase 结束后、Land Phase 开始前必须经过 Approval Gate。
本文件规定 Approval Gate 的**输出格式**和**用户回应判定标准**。

## Approval Gate 的输出格式（**强制模板**）

研究阶段完成后，向用户展示**完整 plan**，至少含以下 5 节：

```md
## 项目规范改进计划

### 1. 调研发现摘要（3-5 句，便于用户快速回顾）
- 现状: ...
- 主要问题: ...
- 识别到的技术栈: ...
- 联合评估了哪些 skill: ...

### 2. 目标结构（树形）
\`\`\`
CONTRIBUTING.md
docs/
  architecture/
    index.md
    rules.md
    ...
  coding/
    index.md
    rules.md
    naming.md
    ...
\`\`\`

### 3. 文件级变更预览（diff 级别，不是抽象描述）
- **新增**:
  - `CONTRIBUTING.md` — 总入口（~30 行）
  - `docs/architecture/index.md` — 导航
  - `docs/architecture/rules.md` — 架构总纲
  - ...
- **修改**:
  - `AGENTS.md` — 删除内嵌规则，改为指向 CONTRIBUTING.md（约 -120 行 / +5 行）
- **迁移**（真搬正文，不只是 mv）:
  - `RULE.md` 的"代码风格"段 → `docs/coding/rules.md`
  - `RULE.md` 的"目录约定"段 → `docs/architecture/rules.md`
- **合并**:
  - `ai/*.md` 共 5 个文件 → `docs/ai-guide/rules.md` + 2 个细则文件
- **删除**:
  - `RULE.md`（内容已全部迁出）

### 4. 决策记录（**自决留痕**）
- 冲突点 1: <best-practice skill A 说 X，B 说 Y>
  - 备选方案: ...
  - 选定: ...
  - 理由: ...
- 内部权衡 1: ...

### 5. 风险与遗留
- 风险: <如"迁移后 AGENTS.md 旧路径在 12 处历史引用，需替换">
- 待用户确认的开放问题: <如有>
```

输出后**显式提问**：

> 以上方案是否可以落地？要不要调整？

## 用户回应判定标准

### ✅ 算明确同意（可以进 Land Phase）

不含保留的肯定表态：

- 「可以落地」「就按这个改」「go ahead」「开始吧」
- 「OK 这个方案，落地」（"OK + 动作动词"）
- 「按这个改吧，xxx 那一点稍微调下」（**部分同意 + 具体调整指令**，重写 plan 后再确认）
- 逐条勾选「1/2/3 可以，4 不要」（**逐项明确**，按勾选执行）

### ❌ 不算同意（必须再问一次）

含糊回应：

- 「嗯」「嗯嗯」「哦」「噢」
- 「ok 吧」「行吧」「好像可以」「应该 ok」
- 「随便」「都行」「你看着办」「你定」
- 只复述了部分计划但没有表态（"所以你要新增 X 和 Y 对吧"）
- 「先这样吧」（**未来时**，不算批准当下落地）
- 「先不动」「再看看」（明确暂停，不进 Land）

### ❌ 内容变更后旧 yes 失效

如果用户对 plan 提了任何修改（哪怕"那个 testing 域改名叫 tests"），
**重写后的 plan 必须重新征求**确认，不能沿用之前对旧 plan 的 yes。

例外：完全没改（如用户只问澄清问题，没要求改 plan）—— 沿用旧 yes 可以。

## Approval Gate 的常见陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 输出 plan 后没等用户回，直接动手 | 越权落地 | **必须**显式提问 + 等待回复 |
| 用户「嗯」就开干 | 用户其实没看完 | 复述决策 + 再问"明确同意落地吗" |
| plan 改了一点不重新问 | 落了用户没批的版本 | 任何修改都要重新征求 |
| 把"建议下一步"段当 plan | 摘要不够细，用户无法判断 | 必须用上面的 5 节模板 |
| 文件级变更只写"新增、修改、迁移、合并、删除"五个字 | 用户看不到具体哪些 | 必须列具体路径 + 摘要 |

## 落地后回执（**Land 阶段完成时**）

```md
## 已落地

### 批准证据
- 用户原话: 「<quote>」
- 时间戳: <ISO ts>

### 实际写入的文件
- 新增: <list>
- 修改: <list>
- 迁移: <list>
- 合并: <list>
- 删除: <list>

### 与批准 plan 的差异
- <若完全一致，写"无">
- <若有差异，列每一处 + 原因>
```

**禁止**：实际写入和批准 plan 有任何未在差异段说明的偏离。
