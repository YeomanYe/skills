# microscope 行为测试用例

验证 `microscope` 是否在"给有内部复杂度的组件写设计文档"时正确触发,产出分层结构(术语表/§1/§2 功能效果+ASCII+核心改动/§3 依赖顺序),并强制跑 persona 可懂性复审;同时不在 API 参考 / README / changelog 等场景误触发。

## 正例触发

### T1. 给组件写设计文档

Prompt：

> 给这个列宽可拖拽的表格组件写一份技术设计文档,讲清楚内部是怎么实现的。

预期：
- 触发本 skill
- 先吃透源码(输入→输出 + 各 case 适配)再动笔
- 产出含:术语表、§1 总览(逻辑+先后顺序)、§2 各 case(功能效果用户视角 + ASCII 图 + 核心改动带因果)、§3 依赖顺序
- 写完派"只懂表格、不懂该技术栈"的 persona 子 agent 复审,按反馈改

### T2. 显式点名

Prompt：

> 用 microscope 给这个导出组件写个设计说明。

预期：触发,按固定结构产出 + persona 复审闭环。

## 反例触发(不应触发)

### N1. API 参考

Prompt：

> 给这个组件的 props 写一份 API 参考表。

预期：**不触发** microscope（那是 API 文档,不是内部设计文档）。

### N2. README / changelog

Prompt：

> 给这个项目写个 README 介绍怎么安装使用。 / 把这次改动写成 changelog。

预期：**不触发**。

## 主流程 / 护栏

### G1. §3 写成数据流被纠正

场景：起草时把"依赖顺序"写成 `collectLeafEntries → leafStates → decoratedColumns` 这种自然数据流。

预期：识别出这是 §1 的料,§3 改写成"互相独立的效果谁压谁、否则冲突"(如 z-index 层叠、点击事件抢占),每条带"判错会出什么问题"。

### G2. 功能效果夹带术语被纠正

场景：功能效果段写"mousedown 记 offsetWidth 再 clamp"。

预期：功能效果改成用户视角"拖动列右边线,这列实时变宽其他列不动",技术词挪进核心改动。

### G3. persona 复审不可跳过

场景：写完文档想直接交付。

预期：必须派"只懂领域、不懂技术栈"的 persona 子 agent 通读、标卡壳处,改到能顺下来才算完成;跳过 = 未完成。
