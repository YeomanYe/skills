# Promote Principles — 9 维 Audit Rubric

> 由 `director-promote` 的 audit / variants mode 自跑。每维 1-5 分,**所有维度必须 [✓] 或 [n/a]**,
> 跳过任何维度等于盲区。<4 分必出修正建议。

## 锚点说明

每维列 1 / 3 / 5 三个锚点。实际打分时落在最接近的锚点上。2 / 4 为中间值。

---

## 1. 标题钩子 (Hook)

> 第一眼能不能让目标平台用户**点开**(列表里)或**停下读完**(信息流里)。

**1 分**(干瘪):
- "新版本发布" / "项目更新"
- "做了个工具"
- 完全没痛点 / 没价值 / 没好奇心

**3 分**(中规中矩):
- "X — 一个 Y 工具"
- 列出功能但缺钩子("浏览器扩展管理工具,支持分组")
- 标题足够长但不抓人

**5 分**(强钩子):
- 痛点直白:"装了 30 个扩展,Chrome 又卡了?"
- 反差/疑问:"为什么我把所有扩展挪到了一个分组?"
- 数字/承诺:"3 秒找出拖垮 Chrome 的那个扩展"

平台差异:
- twitter:钩子句独立成第一行,emoji 用作视觉锚点
- v2ex / Appinn:钩子直接放标题(中文,50 字内,不要 emoji)
- sspai:H1 偏长文体(可以 20-30 字带场景),不要"震惊体"

---

## 2. 一句话价值 (Value Prop)

> 是否清晰说清"解决什么问题 / 给谁用 / 跟同类比凭什么"。

**1 分**(模糊):
- "一个不错的工具"
- "提升效率" / "更方便"(空话)
- 没说目标用户

**3 分**(清晰但平):
- "管理 Chrome 扩展的开关 / 分组"
- 说清功能但没说为什么这个用户需要

**5 分**(清晰且有差异化):
- "本地 + 隐私 + 零云端,装了 30+ 扩展的开发者一眼能上手"
- 说清:做什么 + 给谁用 + 跟同类比什么不一样

---

## 3. 受众匹配 (Audience Fit)

> 文案是否符合**目标平台**的调性。

| 平台 | 调性核心 | 满分要素 | 1 分典型 |
|---|---|---|---|
| twitter | 短钩子 + emoji bullet + hashtag | 280 字内信息密度高 / hashtag 相关 / 有 hero 配图 | 一段长文堆超链接 |
| v2ex | 实用主义 / 不卖关子 / 死链零容忍 | 标题简练 / 正文用 markdown 列表 / 链接已 200 校验 | 营销词 + 死链 + emoji 堆 |
| Appinn(发现频道) | "推荐一个 X" / 痛点切入 / 作者透明 | 第一句"推荐一个我开发的" / 痛点→方案结构 | "我搓了个 / 闲来无事写了" |
| sspai | 长文体 / 6-8 H2 / 不堆超链接 | 结构清晰 / 链接 ≤ 5 / 拒绝"神器""黑科技" | 短文 / bullet 堆 / 营销词 |

**5 分**:文案像在该平台写了 5 年的资深用户写的。
**3 分**:能发但有 1-2 处用力过猛。
**1 分**:复制粘贴一段通用稿到 4 个平台,每个都不像本地用户。

---

## 4. Hero 视觉冲击 (Hero Image)

> 配图是否**抓眼**(出现在 timeline / 列表 / 卡片缩略图里时能吸引点击)。

**1 分**:
- 模糊截屏
- 纯白 / 加载中 / 占位图
- 应用图标本身(没有上下文)
- 截了一段代码块当 hero

**3 分**:
- 实际功能截图但平淡(只有 UI 没有故事)
- 文字太多看不清

**5 分**:
- 一眼能看出**核心价值**(不需要读文字)
- 主体明确 / 留白合理 / 配色有意识
- 包含"使用中"的状态(不是空界面)
- **排版均衡**:元素在画布上均衡分布,视觉重心居中,不堆一角、不留大片空白

> **均衡分布约束的适用边界**:这条只针对**固定尺寸的合成宣传图**(promo tile /
> logo tile / 海报类——agent 在一张画布上摆放元素)。**产品真实截图不适用**:
> 截图是抓现成界面,排版由产品本身决定,不是 agent 摆的,不按本条评判。

无 hero / 不符合 → **must-fix**:调 `director-design mode=mockup` 生成。

---

## 5. 图片内容合规 (Image Safety)

> 截图里是否有**敏感信息**未脱敏。

**must-fix 触发任一**:
- 真实 IP 地址(`192.168.x.x` 也算,内网拓扑泄露)
- 邮箱(尤其工作邮箱)
- 钱包地址 / 余额 / 私钥
- 密码字段(就算被星号遮也要 check)
- 真实姓名 / 手机号 / 身份证号
- API key / token / Authorization header
- 测试环境的真实用户数据(订单号 / 客户名)
- 公司内部命名(项目代号 / 内部域名)

**3 分**:截图基本干净但有 1-2 处可能争议(如显示了浏览器历史的某个 URL)。
**5 分**:全部脱敏 / 用了测试数据 / 信息整洁。
**1 分**:多处敏感信息未处理。

---

## 6. 图片尺寸适配 (Image Dimensions)

> 是否符合**各目标平台**的尺寸规范。

| 平台 / 用途 | 推荐尺寸 | 关键约束 |
|---|---|---|
| twitter 推文配图 | 1200×675 (16:9) | 单图全显示 / 多图自动裁切到 16:9 |
| v2ex 正文配图 | 宽 800-1200 任意高 | GitHub raw 链接(必须已 commit) |
| Appinn 正文配图 | 宽 800-1200 任意高 | 上传到 Discourse 取 `upload://` |
| sspai 题图 | **1600×1200 (4:3)** | 别用 2:1 横图(被裁掉上下) |
| sspai 内嵌图 | 1280×800 PNG | 3 张以内 |
| Chrome Store promo tile small | 440×280 | 必填 |
| Chrome Store promo tile large | 920×680 | 选填 |
| Chrome Store promo tile marquee | 1400×560 | 推广位 |
| Chrome Store screenshots | 1280×800 或 640×400 | 最多 5 张 |
| Edge Store screenshots | 1366×768 / 1920×1080 | 最多 10 张 |

**3 分**:平台基本对得上但有 1-2 处妥协(如缺 marquee)。
**5 分**:全部按规范生成。

**素材无失真(硬约束,任一命中直接 ≤ 2 分)**:

原始截图 / 项目图标接入宣传图时,只能**等比缩放** + **构图性裁切**(为适配平台比例裁成 16:9 / 4:3 等)。**禁止**:
- **非等比拉伸 / 挤压** —— 导致 UI 控件走形、文字变扁/变宽、图标变形、人脸失真
- **裁掉关键内容** —— 为塞进目标尺寸把产品主画面、核心功能区、关键文字裁出框外

平台比例与素材原始比例对不上时:**重新出图,或加留白衬底把素材等比放进目标画布**——不靠拉伸硬塞。

> 区分:**构图性裁切**(裁成平台要求的比例,保留关键内容)是**合法**的,sspai 题图按 4:3 裁、
> Chrome 截图裁切加边框都属此类;**破坏性变形**(拉伸失真 / 裁掉关键内容)才是本约束禁止的。
**1 分**:用 200×200 logo 当 twitter hero 这种明显错误。

---

## 7. 长短文齐备 (Content Coverage)

> 目标平台清单中,**长短文**是否都有。

短文(twitter / 钩子帖):
- ≤ 280 字符,emoji 用作 bullet,1-2 个 hashtag

中文(v2ex / Appinn):
- 200-1000 字,markdown 结构,有标题 + 痛点 + 功能 + 安装链接

长文(sspai / 知乎 / 公众号):
- 1500+ 字,6-8 H2 小节,排版精致

**1 分**:只写了一种长度,4 个平台共用 → twitter 字数超了 / sspai 看着像 v2ex
**3 分**:有 2 个长度版本,缺 1 个
**5 分**:每个目标平台都有专属版本(长度 + 调性都本地化)

---

## 8. CTA 引导 (Call to Action)

> 文案是否含**明确可点击**的下一步动作。

**1 分**:
- 没有任何链接 / 安装入口 / 反馈渠道
- 结尾"希望大家喜欢"这种空 CTA

**3 分**:
- 有 1 个链接但位置不显眼 / 链接太多稀释
- "GitHub: xxx" 直接甩在末尾没说明

**5 分**:
- **1 个主 CTA**(去商店安装 / 去 GitHub star / 去官网试用)
- 链接旁有动作动词("立即安装" / "下载 .crx" / "提反馈")
- 反馈渠道清晰(GitHub Issues / 邮箱 / 论坛)
- 链接已 `curl -sI` 200 校验

平台差异:
- twitter:hashtag + 主链接(1 个)
- v2ex:Markdown 链接,2-3 个主链接(商店/源码)
- Appinn:精简 2 链接(商店 + 源码),不堆
- sspai:H2 末尾"安装方式" + "反馈渠道" 两节

---

## 9. 平台原生感 (Native Feel)

> 是否避免 **AI slop**(让平台用户一眼看出这是机器写的 / 营销稿)。

**1 分**(AI slop 高发):
- "神器" / "秒杀" / "吊打" / "黑科技" / "颠覆"
- "懒人福音" / "效率神器" / "必备神器"
- emoji 堆叠("🚀🎉🔥💯🌟 全新版本!!!")
- "大家好,我是 X,今天给大家带来"
- 每段都用"!"结尾
- 全是"惊人""震撼""革命性"形容词
- "我搓了个 / 周末做了个"(自降身价,Appinn 反感)

**3 分**(平淡但不出戏):
- 偶有 1-2 处用力过猛
- 整体能看出是人写的但缺少个性

**5 分**(原生):
- 用词朴素具体("有一次我开了 30 个扩展,Chrome 内存涨到 4G")
- 痛点用故事讲(不是堆形容词)
- emoji 克制(twitter 用作 bullet 标记,其他平台几乎不用)
- 链接不堆(2-3 个主链接 + 一个反馈)
- 字里行间有"我是个开发者 / 我也用这个 / 我自己也踩过这坑"的真实感

## Aggregate 评分

加权:9 维等权,取算数平均。

| Aggregate | Verdict | 行动 |
|---|---|---|
| ≥ 4.5 | `ready` | 直接 dispatch |
| 4.0-4.4 | `ready-with-fixes` | should-fix 列清单,用户决定是否修后再发 |
| 3.0-3.9 | `needs-revision` | must-fix 列清单,必须修后才能 dispatch |
| < 3.0 | `blocked` | 材料整体不达标,回 draft 或 variants |

特殊触发(任一直接降级为 `blocked`):
- 维度 5(图片内容合规)= 1 分
- 维度 4(Hero 视觉冲击)< 3 且无 hero 图

## Reference 案例

- ✅ 成功案例:Ext Helper Appinn topic 84782 — 满分案例,见 `platforms/appinn.md`
- ✅ 参考案例:UniMail 多平台宣发 — 从文案准备到最终发布的完整回归案例:
  - 文案口径必须全平台同步:用户纠正"邮箱扩展"、"支持侧边栏邮件列表展示"、Chrome/Firefox/Edge 支持说法后,所有平台草稿都要重新 QA。
  - 宣传图含真实 UI 时按截图处理,优先级高于普通截图;有内容丰富的 promo-with-UI 图时,不要额外塞长图。
  - 预览通过不等于发布完成:X 要 status URL,V2EX 可能卡邮箱验证,Appinn 可能进入待处理审核,Product Hunt 需要 launch 日期,sspai 需要内容就绪后的当前明确发布确认。
  - Playwriter 断连后必须 reset、按 URL 重新匹配页面、重读状态,不能凭旧页面编号继续点。
  - 回执格式必须区分 `published` / `scheduled` / `submitted-to-review` / `ready-for-confirmation` / `blocked`。
